# Резервное копирование PostgreSQL

Команды рассчитаны на PostgreSQL-контейнер официального образа с
`POSTGRES_USER` и `POSTGRES_DB`. Пароль не передаётся в аргументах или выводе.
Архив содержит данные пользователей: храните его в закрытом каталоге,
шифруйте внешние копии и ограничивайте доступ. Копия на том же сервере не
защищает от потери сервера или диска.

## Создание копии

Создайте закрытый каталог хранения заранее. Укажите новый абсолютный путь:

```bash
bash scripts/backup-db.sh healthy_bot_db /srv/healthy-backups/pre-release-2026-10-02.dump
```

Скрипт использует согласованный снимок `pg_dump`, формат custom, проверяет
читаемость архива и публикует файл только после успешного завершения.
Права файла — только владельцу; существующий архив не перезаписывается.
Затем скопируйте архив в отдельное защищённое хранилище. Проверка списка
архива сама по себе не подтверждает возможность восстановления.

## Проверка восстановления

Предпочтителен отдельный PostgreSQL 16 без рабочих данных. У контейнера
должно быть достаточно места для восстановленной базы. Команда создаёт новую
БД и отказывается использовать существующую:

```bash
bash scripts/verify-db-backup.sh healthy-rel01-postgres /srv/healthy-backups/pre-release-2026-10-02.dump restorecheck_pre_release_20261002
```

Восстановление останавливается на первой ошибке; рабочие базы не очищаются.
Тестовая БД остаётся для проверки. При ошибке она также остаётся: повторяйте
проверку под новым именем, сначала выяснив причину.

После восстановления проверьте число пользователей, записей еды, воды и веса,
черновики и очередь, выбранные дни отчётов и связи между таблицами. Для точного
сравнения с рабочей БД учитывайте записи, созданные после начала снимка.
Проверку приложения выполняйте с отключёнными отправкой сообщений, scheduler
и AI-worker: восстановленная очередь не должна отправлять старые задания.

Зафиксируйте дату, версию PostgreSQL, путь и размер копии, результат проверки
и место внешнего хранения в плане развития. Настройка расписания, сроков
хранения и уведомлений о неудачном копировании — отдельный следующий шаг.

## Перед релизом

Нужны копия именно рабочей БД и подтверждённое восстановление этой копии.
Локальная репетиция на синтетических данных проверяет инструменты, но не
подтверждает актуальность и полноту рабочей резервной копии.
