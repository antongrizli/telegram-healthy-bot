Архитектурные контракты: [клавиатуры](architecture/keyboards.md),
[надёжность](architecture/reliability.md).

## Как ведём прогресс

- У каждой задачи постоянный ID, приоритет, статус и критерий завершения.
- «Реализовано локально» означает, что изменения есть в рабочем дереве и проверены
  в указанном объёме. Это не подтверждает работу на сервере.
- «Частично» означает, что выполнена только часть критерия завершения.
- «Запланировано» — реализация не начата. «Отложено» — сознательно исключено из
  ближайших этапов.
- После каждого согласованного этапа обновляем статусы, результаты проверок и
  следующий шаг. Ошибки проверок записываем в соответствующую задачу.
- Выкладку закрываем только после успешной проверки конкретной версии на сервере.
  Настроенный CI не считается выполненным CI.
- Этот документ не запускает автоматический мониторинг или выкладку.

Рекомендуемый следующий шаг: **REL-01**, затем **REL-02 → REL-03**.
Проверки интерфейса на синтетических данных не заменяют запуск в реальном Telegram.

Инструкция копирования: [резервные копии](operations/backups.md).
Инструкция выпуска: [релиз и откат](operations/release.md).
Для продолжения релизных проверок необходимы доступ к серверу и путь внешнего
хранения. Отправка отдельной ветки и создание PR отклонены автоматической
проверкой разрешений: требуется явное подтверждение передачи текущих изменений
в `https://github.com/antongrizli/telegram-heathy-bot`. Изменения ещё не отправлены
в GitHub: push в `main` публикует `latest`,
который может автоматически установить Watchtower. Сначала проверить CI через PR,
затем копию рабочей БД и согласованную версию релиза.

Артефакт локальной репетиции: `/private/tmp/healthy-rel02.lDLVXo/rehearsal.dump`
(3946 байт, права `0600`, синтетические данные). БД `restorecheck_rel02` сохранена
в остановленном тестовом контейнере для проверки. Это не рабочая резервная копия.
