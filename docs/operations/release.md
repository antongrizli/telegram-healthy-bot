# Проверка и выпуск пакета надёжности

## До выпуска

1. В PR текущей версии должны пройти Python-тесты с PostgreSQL 16,
   мобильные проверки 7 языков и сборка Docker. PR и ручной workflow
   не публикуют образ; push в main или релизный тег публикуют.
2. На сервере создайте копию рабочей БД и восстановите её отдельно по
   [инструкции](backups.md). Зафиксируйте внешнее место хранения.
3. Сохраните текущий digest образа и настройки запуска. Не публикуйте
   `docker inspect` целиком: он содержит переменные окружения и секреты.
   Для записи версии достаточно:

   ```bash
   docker inspect --format '{{.Image}}' healthy_bot_app
   docker image inspect --format '{{json .RepoDigests}}' antongrizli/telegram-heathy-bot:latest
   ```

4. Проверьте политику Watchtower. Слияние в main изменяет latest и может
   вызвать автоматическую выкладку. Момент публикации согласуйте с окном
   проверки; не рассчитывайте на ручной перезапуск после публикации.

## Проверка после обновления

Зафиксируйте commit, digest, время запуска и результаты:

- `/health` отвечает 200; в логах нет ошибок обновления схемы.
- WebApp открывается через Telegram, страницы прогресса и достижений доступны.
- Создайте и подтвердите тестовый приём пищи: одна запись, без дублей кнопок.
- Оставьте черновик, перезапустите приложение и подтвердите его один раз.
- Выберите понедельник для отчёта; после перезапуска значение сохранено.
- Проверьте тестовое напоминание и доставку задания из очереди.
- Некорректный ввод даёт понятную ошибку, без текста SQL и исключений.
- Старые карты показывают пояснение; пустой дневник не получает оценку здоровья.

Используйте отдельный тестовый Telegram-профиль, чтобы не менять рабочие записи.
Тесты API и браузера не подтверждают доставку реальным Telegram-клиентом.

## Откат

Остановите обновление через Watchtower, верните ранее сохранённый digest и
запустите один экземпляр бота. Новые изменения схемы аддитивны; восстановление
старой копии БД при обычном откате приложения не требуется и потеряет новые
записи. Обратный запуск старой версии требует отдельной проверки совместимости.

Старая версия не использует журнал AI-попыток, поэтому после отката её лимиты
не учитывают новые неудачные попытки. Старая версия также может снова менять
выбранный понедельник при запуске. При откате сохраните эти настройки отдельно
и ограничьте AI-вызовы до проверки. Ошибки схемы или данных сначала расследуйте
на копии; рабочую БД автоматически не очищайте и не восстанавливайте.
